# crm-lite — contesto di progetto

## Stack e versioni
- Next.js 16.3.4, App Router, TypeScript (`typescript@^5`)
- Package manager: npm (unico lockfile presente: `package-lock.json`)
- Database: PostgreSQL su Neon (cloud, serverless) — niente Postgres/Docker locale, vedi `DATABASE_URL` in `.env`
- ORM: Prisma 7.10.0, con driver adapter esplicito `@prisma/adapter-pg` (Prisma 7 richiede un adapter, non usa più il query engine binario di default delle versioni precedenti)

## Convenzioni specifiche di questa versione di Next.js
- Il file di protezione route si chiama `proxy.ts` (non `middleware.ts`), ed è in `src/proxy.ts`. In Next 16 `middleware.ts`/`export function middleware` è deprecato a favore di `proxy.ts`/`export function proxy` (funziona ancora ma con warning di build). Va messo nella cartella genitore di `app/`: qui `app` sta in `src/app`, quindi il file va in `src/`, **non** nella root del progetto — in root verrebbe ignorato silenziosamente.
- Il runtime di default del proxy è **Node.js**, non Edge (diversamente dalle versioni precedenti di Next, dove il middleware girava su Edge Runtime). Impostare `runtime` nel proxy genera un errore: non è configurabile.

## Autenticazione e sessioni
- Sessioni custom basate su cookie firmato (`iron-session`) + tabella `Session` su Prisma. **Non** Auth.js/NextAuth (rimosso: era incompatibile con sessioni "database" quando l'unico provider è Credentials, e comunque non permetteva la revoca immediata voluta).
- Motivo della scelta: revoca lato server immediata (requisito: poter disconnettere subito un utente da tutti i dispositivi) — non ottenibile con JWT stateless, dove il token resta valido finché non scade.
- File coinvolti:
  - `src/lib/session.ts` — `login()`, `logout()`, `getCurrentUser()`. `getCurrentUser()` valida sempre la sessione contro il DB (non solo il cookie); include anche `user.role` nella query. Contiene anche il fix di pulizia cookie: se la sessione risulta assente/scaduta, prova a cancellare il cookie (`cookieSession.destroy()` in un `try/catch`, perché un Server Component in fase di render non può scrivere cookie — vedi sotto).
  - `src/lib/session-cookie.ts` — costante `SESSION_COOKIE_NAME`, condivisa tra `session.ts` e `proxy.ts` per non duplicare il nome del cookie.
  - `src/proxy.ts` — controllo veloce di sola presenza del cookie (nessuna query DB/Prisma, che nel proxy va evitata a prescindere dal runtime): protegge le route riservate e rimanda via da `/login` chi ha già un cookie.
  - `src/app/api/session/clear/route.ts` — Route Handler che cancella davvero il cookie (chiama `logout()`) e reindirizza a `/login`. Esiste perché Next.js vieta di scrivere/cancellare cookie durante il render di un Server Component; senza questo passaggio, una sessione invalida con cookie ancora presente farebbe rimbalzare l'utente all'infinito tra pagina protetta e `/login` (il proxy vede il cookie e rimanda alla pagina, la pagina vede la sessione invalida e rimanda a login). Va usato per qualunque redirect da sessione-non-valida, non solo `redirect("/login")` diretto.
  - `src/lib/authorization.ts` — vedi sezione sotto.
- `SESSION_SECRET` in `.env` (minimo 32 caratteri, generato con `openssl rand -base64 32`): password di cifratura del cookie iron-session, nessun default/fallback in codice.

## Autorizzazione basata sul ruolo
- Regola: `Role.level = 1` → Admin, qualunque altro valore → utente non-admin (Venditore). Confermato nel seed (`prisma/seed.ts`): Amministratore `level: 1`, Venditore `level: 2`.
- Helper in `src/lib/authorization.ts`:
  - `requireAuth()` — richiede utente loggato, altrimenti redirect (via `/api/session/clear`, non `/login` diretto — stesso motivo del loop spiegato sopra). Usabile in Server Component e Server Action.
  - `requireAdmin()` — come sopra, più controllo `role.level === 1`; se fallisce, redirect a `/unauthorized`.
  - `isAdmin(user)` — funzione pura, nessun redirect, solo `true`/`false`. Da usare **solo** per mostrare/nascondere UI, mai come unico controllo di sicurezza.
- Principio da rispettare sempre: ogni Server Action che modifica dati sensibili deve chiamare `requireAuth()`/`requireAdmin()` al proprio interno lato server — non fidarsi mai del fatto che la UI nasconda un bottone o un'opzione.

## Schema dati
Definizione completa in `prisma/schema.prisma`; qui solo un riferimento sintetico:
- `Role` — ruoli utente (level determina i permessi, vedi sopra)
- `User` — utenti di sistema (credenziali, anagrafica, `roleId`)
- `Company` — aziende clienti
- `Contact` — contatti, opzionalmente collegati a una `Company`
- `DealState` — stati possibili di una trattativa (lookup table: nuovo/contattato/proposta/vinta/persa...)
- `Deal` — trattativa/opportunità commerciale (valore, stato, proprietario, contatto)
- `ActivityType` — tipologie di attività (chiamata/email/meeting/nota...)
- `Activity` — attività svolte su una `Deal`
- Nota di design: `Activity.userId` è tenuto distinto da `Deal.userId` apposta, per non perdere la storia di chi ha svolto un'attività quando la deal viene riassegnata a un altro utente.

## Route protette
- Configurazione in `src/proxy.ts`, `matcher: ["/dashboard/:path*", "/companies/:path*", "/login"]`.
- Protette (richiedono cookie di sessione): `/dashboard`, `/companies`.
- Pubblica esclusiva (redirect via se già loggato): `/login`.
- Il matcher va aggiornato manualmente ogni volta che si crea una nuova sezione protetta del CRM — non è automatico in base alle pagine esistenti.

## CRUD Company
- Pattern: Server Component per la lettura (`app/companies/page.tsx`, `app/companies/[id]/edit/page.tsx`) + Server Actions per la scrittura (`app/companies/actions.ts`) + Client Component solo dove serve interattività (`CompanyForm`, `DeleteCompanyButton`).
- `requireAuth()` (non `requireAdmin()`) sia nelle pagine sia dentro ogni Server Action di `actions.ts`: la gestione anagrafica aziende non è riservata agli admin, ma resta un'operazione che modifica dati sensibili e quindi non può fidarsi della sola UI/proxy — vedi principio in "Autorizzazione basata sul ruolo".
- **Nota discrepanza schema**: la richiesta originale del CRUD ipotizzava `address` e `piva` come campi opzionali (`String?`). Lo schema realmente presente in `prisma/schema.prisma` li ha invece entrambi obbligatori, con `piva` anche `@unique`. Non è stata fatta alcuna migrazione: lo schema Zod in `actions.ts` segue lo schema DB reale (tutti e tre i campi `name`/`address`/`piva` obbligatori). Se in futuro si vuole davvero renderli opzionali, serve una migrazione Prisma esplicita, non solo una modifica alla validazione.
- Gli errori Prisma noti vengono tradotti in messaggi utente dentro le Server Action invece di far esplodere l'app: `P2002` (violazione unicità `piva`) su create/update, `P2003` (FK: azienda con `Contact` collegati) su delete. Ogni Server Action ritorna sempre `{ success, error? }`, mai un throw per errori di validazione/vincolo attesi.
- `CompanyForm` è condiviso tra creazione e modifica: sceglie `createCompany` o `updateCompany.bind(null, companyId)` in base alla presenza di `defaultValues`, usa `useActionState` per pending state ed errori di validazione per campo, e fa `router.push("/companies")` lato client dopo un esito positivo (l'azione non chiama `redirect()` di proposito, altrimenti il client non riceverebbe mai lo stato di successo).
- `zod` è stato aggiunto come dipendenza diretta in `package.json` (prima presente solo transitivamente via `prisma`).

## Design system (Northline CRM)
- Fonte: `design-system.md` in root (estratto da un mockup Figma/Claude Design). Per ora è stata portata solo l'infrastruttura di token in `src/app/globals.css` + `src/app/layout.tsx` — nessun componente visivo (Button, Card, ecc.) è stato ancora costruito.
- **Niente `tailwind.config.ts`, di proposito**: questo progetto usa Tailwind CSS **v4**, che ha abbandonato la config JS a favore della configurazione CSS-first via `@theme` (vedi `src/app/globals.css`). Un `tailwind.config.ts` richiederebbe la direttiva `@config` e andrebbe in conflitto/duplicazione con l'unico blocco `@theme inline` già presente. Se in futuro si è tentati di creare `tailwind.config.ts` per aggiungere token "alla v3", è quasi certamente l'abitudine sbagliata per questa versione — estendere invece `@theme` in `globals.css`.
- Tutti i colori/radius/shadow/spacing del design system sono token nominati dentro l'unico blocco `@theme inline` di `globals.css` (namespace Tailwind v4: `--color-*`, `--radius-*`, `--shadow-*`, `--spacing-*`, `--font-*`). I nomi ricalcano quelli del documento (`primary`, `surface-1/2/3`, `text-primary/secondary/muted`, `success`/`warning`/`danger` (+varianti `-bg`), `border`/`border-subtle`), con due aggiunte non esplicitamente elencate nella richiesta ma presenti nel documento: `primary-subtle` (`#26375C`, fondo tenue) e `primary-soft` (`#B9CCFF`, testo/link su sfondo scuro).
- `--color-background` è stato riusato (stesso nome dello scaffold di create-next-app) ma ripuntato al colore pagina del design system (`#0F171F`); è stato aggiunto un alias `--color-foreground: var(--color-text-primary)` solo per **retrocompatibilità** con `src/app/page.tsx` (pagina placeholder di create-next-app, non ancora toccata), che usa ancora le classi `bg-foreground`/`text-foreground`. Il blocco `@media (prefers-color-scheme: dark)` dello scaffold è stato rimosso: il design system non definisce una variante light (`design-system.md`, sezione "Non definito").
- Spacing e radius sono scale **nominali aggiuntive** (`--radius-checkbox/tooltip/icon/control/panel/card/modal/pill`), non sostituiscono la scala numerica di default di Tailwind (`p-4`, `gap-2`, `rounded-sm`, ecc. restano invariati e continuano a funzionare esattamente come prima).
- **Bug reale trovato e corretto costruendo `components/ui/`**: la prima scala `--spacing-*` (nomi t-shirt semplici: `--spacing-xs`, `--spacing-md`, `--spacing-lg`, ecc.) sembrava sicura per analogia con `--radius-*`, ma **non lo è**. Tailwind v4 usa lo stesso namespace `--container-*` (chiavi `xs`/`sm`/`md`/`lg`/`xl`/`2xl`/`3xl`/…) per `max-w-*`/`min-w-*`/`w-*`/`h-*`, e quando una chiave esiste sia in `--spacing-*` sia in `--container-*` **vince `--spacing-*`**. Il risultato: `--spacing-md: 14px` aveva silenziosamente rotto `max-w-md` in tutto il progetto (compresi `src/app/page.tsx`, non toccato, e `CompanyForm.tsx`) portandolo da 28rem a 14px. Non è successo con `--radius-*` solo perché quei nomi (`checkbox`, `card`, `modal`, ecc.) non sono nomi t-shirt e non potevano collidere. **Regola per qualunque token futuro**: prima di aggiungere una chiave a un namespace Tailwind esistente (`--spacing-*`, `--text-*`, `--radius-*`, `--shadow-*`, `--tracking-*`, …), verificare che quel nome non compaia già nello scaffold di default di Tailwind per QUALSIASI utility che condivide lo stesso namespace (non solo quella che si sta usando in quel momento) — in caso di dubbio, usare un nome non ambiguo invece di un t-shirt size. Fix applicato: tutta la scala `--spacing-*` custom ora usa il prefisso `nl-` (lo stesso delle `@keyframes nl-pulse`/`nl-flash` del mockup originale), quindi `gap-nl-md`, `py-nl-control-y`, ecc. — mai `gap-md`/`py-control-y` nudi.
- Font: `Fraunces` (`--font-display`), `Inter` (`--font-sans`), `IBM Plex Mono` (`--font-mono`) caricati via `next/font/google` in `src/app/layout.tsx` con solo i pesi effettivamente usati nel documento (400/500/600, 400/500/600/700, 400/500). Sostituiscono Geist/Geist Mono dello scaffold iniziale, non più referenziati da nessuna parte.
- `--gradient-logo` (gradiente logo) è una CSS custom property in `:root`, fuori dal blocco `@theme`: `--gradient-*` non è un namespace riconosciuto da Tailwind v4 e non genererebbe alcuna utility; va usato con una classe arbitraria (`bg-[image:var(--gradient-logo)]`) quando si costruirà il componente Logo.
- Non ancora portate (rimandate a quando si costruiranno i componenti che le usano): le animazioni `nl-pulse`/`nl-flash` (pallino "trattativa calda", flash riga nuova trattativa) — sono comportamento di componente, non token di base.
- `lucide-react` aggiunto come dipendenza per le icone: il documento specifica size 15–19px e `strokeWidth` 1.8, da passare come props a ogni icona (vedi uso in `src/app/ui-preview/page.tsx`).

  - Sparkline di `MetricCard`: il documento non definisce un token "dim" per le barre non correnti — uso `bg-primary/35` (opacità derivata dal colore pieno via modificatore Tailwind), come suggerito in alternativa. Non definisce nemmeno una larghezza barra: uso `flex-1` (barre equidistribuite) invece di un valore in px, per non inventare un numero assente dal documento.
  - Nuovi token in `globals.css` per Card/Table: `--text-body: 13px` (riga tabella, task, dettagli, card trattativa — distinto da `--text-ui: 13.5px` che è specifico di bottoni/input), `--text-metric: 26px` (valore card metrica), `--radius-bar: 2px` (angoli superiori barre sparkline, via `rounded-t-bar`), `--spacing-nl-expand-indent: 52px` (padding-left riga espansa tabella). `--spacing-nl-control-x-login` (13px) è stato riusato anche per il padding orizzontale di `DealCard` (stesso valore letterale nel documento).
