# crm-lite — contesto di progetto

## Stack e versioni
- Next.js 16.3.4, App Router, TypeScript (`typescript@^5`)
- Package manager: npm (unico lockfile presente: `package-lock.json`)
- Database: PostgreSQL su Neon (cloud, serverless) — niente Postgres/Docker locale, vedi `DATABASE_URL` in `.env`
- ORM: Prisma 7.10.0, con driver adapter esplicito `@prisma/adapter-pg` (Prisma 7 richiede un adapter, non usa più il query engine binario di default delle versioni precedenti)

## Convenzioni specifiche di questa versione di Next.js
- Il file di protezione route si chiama `proxy.ts` (non `middleware.ts`), ed è in `src/proxy.ts`. In Next 16 `middleware.ts`/`export function middleware` è deprecato a favore di `proxy.ts`/`export function proxy` (funziona ancora ma con warning di build). Va messo nella cartella genitore di `app/`: qui `app` sta in `src/app`, quindi il file va in `src/`, **non** nella root del progetto — in root verrebbe ignorato silenziosamente.
- Il runtime di default del proxy è **Node.js**, non Edge (diversamente dalle versioni precedenti di Next, dove il middleware girava su Edge Runtime). Impostare `runtime` nel proxy genera un errore: non è configurabile.

## Autenticazione e sessioni
- Sessioni custom basate su cookie firmato (`iron-session`) + tabella `Session` su Prisma. **Non** Auth.js/NextAuth (rimosso: era incompatibile con sessioni "database" quando l'unico provider è Credentials, e comunque non permetteva la revoca immediata voluta).
- Motivo della scelta: revoca lato server immediata (requisito: poter disconnettere subito un utente da tutti i dispositivi) — non ottenibile con JWT stateless, dove il token resta valido finché non scade.
- File coinvolti:
  - `src/lib/session.ts` — `login()`, `logout()`, `getCurrentUser()`. `getCurrentUser()` valida sempre la sessione contro il DB (non solo il cookie); include anche `user.role` nella query. Contiene anche il fix di pulizia cookie: se la sessione risulta assente/scaduta, prova a cancellare il cookie (`cookieSession.destroy()` in un `try/catch`, perché un Server Component in fase di render non può scrivere cookie — vedi sotto).
  - `src/lib/session-cookie.ts` — costante `SESSION_COOKIE_NAME`, condivisa tra `session.ts` e `proxy.ts` per non duplicare il nome del cookie.
  - `src/proxy.ts` — controllo veloce di sola presenza del cookie (nessuna query DB/Prisma, che nel proxy va evitata a prescindere dal runtime): protegge le route riservate e rimanda via da `/login` chi ha già un cookie.
  - `src/app/api/session/clear/route.ts` — Route Handler che cancella davvero il cookie (chiama `logout()`) e reindirizza a `/login`. Esiste perché Next.js vieta di scrivere/cancellare cookie durante il render di un Server Component; senza questo passaggio, una sessione invalida con cookie ancora presente farebbe rimbalzare l'utente all'infinito tra pagina protetta e `/login` (il proxy vede il cookie e rimanda alla pagina, la pagina vede la sessione invalida e rimanda a login). Va usato per qualunque redirect da sessione-non-valida, non solo `redirect("/login")` diretto.
  - `src/lib/authorization.ts` — vedi sezione sotto.
- `SESSION_SECRET` in `.env` (minimo 32 caratteri, generato con `openssl rand -base64 32`): password di cifratura del cookie iron-session, nessun default/fallback in codice.

## Autorizzazione basata sul ruolo
- Regola: `Role.level = 1` → Admin, qualunque altro valore → utente non-admin (Venditore). Confermato nel seed (`prisma/seed.ts`): Amministratore `level: 1`, Venditore `level: 2`.
- Helper in `src/lib/authorization.ts`:
  - `requireAuth()` — richiede utente loggato, altrimenti redirect (via `/api/session/clear`, non `/login` diretto — stesso motivo del loop spiegato sopra). Usabile in Server Component e Server Action.
  - `requireAdmin()` — come sopra, più controllo `role.level === 1`; se fallisce, redirect a `/unauthorized`.
  - `isAdmin(user)` — funzione pura, nessun redirect, solo `true`/`false`. Da usare **solo** per mostrare/nascondere UI, mai come unico controllo di sicurezza.
- Principio da rispettare sempre: ogni Server Action che modifica dati sensibili deve chiamare `requireAuth()`/`requireAdmin()` al proprio interno lato server — non fidarsi mai del fatto che la UI nasconda un bottone o un'opzione.

## Filtro dati per ruolo su Deal e Activity
- **Regola di prodotto**: Admin vede tutte le trattative/attività di tutti; un non-admin (Venditore) vede solo le proprie. Prima di questo step `requireAdmin()`/`isAdmin()` esistevano in `authorization.ts` ma non erano chiamati da nessuna pagina/query reale — ogni utente loggato vedeva tutto, il filtro per ruolo non era implementato nonostante lo schema lo permettesse già (`Deal.userId`, `Activity.userId`).
- Helper aggiunto in `src/lib/authorization.ts`: `ownRowsWhere(user)` → `{}` per l'admin, `{ userId: user.userId }` per un non-admin. Un solo helper per entrambi i modelli (stessa regola di visibilità), anche se il campo `userId` ha un significato diverso nei due casi — **da usare con il campo giusto in ogni query**:
  - `Deal.userId` = proprietario della trattativa.
  - `Activity.userId` = chi ha svolto l'attività (l'esecutore), **non** il proprietario della deal collegata — coerente con la nota di design già presente più sotto ("Activity.userId tenuto distinto da Deal.userId apposta"). Un non-admin vede quindi solo le attività che ha svolto lui, anche su una propria trattativa; non vede quelle svolte da un collega sulla stessa trattativa.
- **Dove è applicato** (lettura, `where: ownRowsWhere(user)`):
  - `app/(dashboard)/deals/page.tsx` — `deal.findMany` (lista/Kanban trattative).
  - `app/(dashboard)/activities/page.tsx` — sia `activity.findMany` (lista attività) sia `deal.findMany` (opzioni del select trattativa nel form di creazione attività): un non-admin deve poter scegliere solo tra le trattative che vede già in Deals, altrimenti il dropdown rivelerebbe l'esistenza di trattative altrui.
  - `components/layout/ActivityPanel.tsx` — `activity.findMany` (le 4 righe di "Attività recente"), stesso criterio: solo le attività svolte dall'utente corrente per un non-admin.
- **Dove NON è applicato, di proposito** (per restare nello scope di questo step — Deal/Activity, non un redesign completo dei permessi):
  - `Company`/`Contact`: restano dati di team, nessun filtro (scelta di design già esistente e documentata sotto per `Contact`; per `Company` non c'è comunque un `userId` proprio).
  - `app/(dashboard)/companies/page.tsx`: l'aggregazione `contacts.deals` per le metriche/righe espandibili della tabella Aziende **non** è filtrata — un non-admin vede ancora valore/conteggio trattative di tutta l'azienda, incluse trattative altrui. Gap noto, non risolto qui.
  - `app/(dashboard)/dashboard/page.tsx`: tutte le query `deal.aggregate`/`groupBy`/`findMany` restano su tutti i dati, non filtrate per utente. In particolare "Squadra commerciale" è per costruzione un confronto tra utenti: filtrarla per un non-admin la svuoterebbe di senso (mostrerebbe solo sé stesso) — richiede una decisione di prodotto a parte (filtrare le altre card ma nascondere "Squadra commerciale" per un non-admin, o altro), non presa in questo step.
- **Scrittura, non solo lettura** — stesso principio già enunciato sopra ("mai fidarsi solo della UI"): nascondere le righe altrui dalle liste non basta, le Server Action devono rifiutarle anche se invocate direttamente con un id non proprio:
  - `deals/actions.ts` → `updateDealState` (drag&drop Kanban / select stato): il `where` dell'`update()` ora è `{ dealId, ...ownRowsWhere(user) }`, non solo `{ dealId }`. Se la riga non è dell'utente, Prisma non la trova e ricade nello stesso ramo `P2025` già gestito per una Deal davvero cancellata — nessun messaggio diverso, per non rivelare a un non-admin che una trattativa altrui esiste.
  - `activities/actions.ts` → `createActivity`: aggiunta una query preliminare (solo per i non-admin, `isAdmin(user)` salta il controllo per l'admin) che verifica `deal.userId === user.userId` prima di creare l'attività, altrimenti stesso messaggio di errore già usato per una FK non più valida ("La trattativa selezionata non è più valida."). Non basta filtrare le opzioni del dropdown lato pagina: un non-admin potrebbe altrimenti inviare un `dealId` altrui chiamando l'azione direttamente.
  - Non esistono ancora `updateDeal`/`deleteDeal`/`updateActivity`/`deleteActivity` in questo progetto (solo `createDeal`/`updateDealState` e `createActivity`, vedi i file sopra): se in futuro verranno aggiunte, andranno protette con lo stesso pattern `where: { ..., ...ownRowsWhere(user) }`.
- **`ActivityPanel` è diventato Server Component "figlio" di `(dashboard)/layout.tsx`**, non fa una propria `getCurrentUser()`: il layout la fa già una volta per la Topbar (vedi sezione Autenticazione) e ora passa lo stesso `user` (tipo `SafeUser | null`) anche ad `ActivityPanel` via prop — un'unica query di sessione per request, non una per componente. Se `user` è `null` (sessione non valida in un giro di render prima del redirect della pagina), `ActivityPanel` non esegue alcuna query Prisma e mostra solo l'intestazione della sezione vuota, invece di interrogare il DB senza un utente reale con cui filtrare.

## Schema dati
Definizione completa in `prisma/schema.prisma`; qui solo un riferimento sintetico:
- `Role` — ruoli utente (level determina i permessi, vedi sopra)
- `User` — utenti di sistema (credenziali, anagrafica, `roleId`)
- `Company` — aziende clienti
- `Contact` — contatti, opzionalmente collegati a una `Company`
- `DealState` — stati possibili di una trattativa (lookup table: i 4 stati realmente seedati in `prisma/seed.ts` sono `nuovo`/`proposta`/`vinto`/`perso`, non esiste uno stato "contattato")
- `Deal` — trattativa/opportunità commerciale (valore, stato, proprietario, contatto)
- `ActivityType` — tipologie di attività: solo 3, fissate e seedate in `prisma/seed.ts` (`chiamata`/`email`/`meeting`), nessun tipo "nota" e nessuna gestione dinamica (vedi sezione CRUD Activity più sotto)
- `Activity` — attività svolte su una `Deal`
- `Session` — sessioni custom su cookie firmato (vedi sezione Autenticazione sopra: non è Auth.js/NextAuth)
- `Attachment` — allegato caricato su storage esterno S3-compatible (`storageKey` univoco, distinto dal `fileName` originale), con `uploadedByUserId` obbligatorio. Nello schema `dealId`/`contactId` sono entrambi `Int?` (nessun vincolo DB "esattamente uno dei due"), ma **di prodotto un Attachment si collega solo a una `Deal`**: `contactId` resta nel modello per compatibilità/futuro ma nessuna Server Action lo valorizza — vedi sezione "Storage file (R2)" per i dettagli e la correzione di scope rispetto a una prima versione che considerava anche `Contact`
- Nota di design: `Activity.userId` è tenuto distinto da `Deal.userId` apposta, per non perdere la storia di chi ha svolto un'attività quando la deal viene riassegnata a un altro utente.

## Route protette
- Configurazione in `src/proxy.ts`, `matcher: ["/dashboard/:path*", "/companies/:path*", "/contacts/:path*", "/login"]`.
- Protette (richiedono cookie di sessione): `/dashboard`, `/companies`, `/contacts`.
- Pubblica esclusiva (redirect via se già loggato): `/login`.
- Il matcher va aggiornato manualmente ogni volta che si crea una nuova sezione protetta del CRM — non è automatico in base alle pagine esistenti.

## CRUD Company
- Pattern: Server Component per la lettura (`app/companies/page.tsx`, `app/companies/[id]/edit/page.tsx`) + Server Actions per la scrittura (`app/companies/actions.ts`) + Client Component solo dove serve interattività (`CompanyForm`, `DeleteCompanyButton`).
- `requireAuth()` (non `requireAdmin()`) sia nelle pagine sia dentro ogni Server Action di `actions.ts`: la gestione anagrafica aziende non è riservata agli admin, ma resta un'operazione che modifica dati sensibili e quindi non può fidarsi della sola UI/proxy — vedi principio in "Autorizzazione basata sul ruolo".
- **Nota discrepanza schema**: la richiesta originale del CRUD ipotizzava `address` e `piva` come campi opzionali (`String?`). Lo schema realmente presente in `prisma/schema.prisma` li ha invece entrambi obbligatori, con `piva` anche `@unique`. Non è stata fatta alcuna migrazione: lo schema Zod in `actions.ts` segue lo schema DB reale (tutti e tre i campi `name`/`address`/`piva` obbligatori). Se in futuro si vuole davvero renderli opzionali, serve una migrazione Prisma esplicita, non solo una modifica alla validazione.
- Gli errori Prisma noti vengono tradotti in messaggi utente dentro le Server Action invece di far esplodere l'app: `P2002` (violazione unicità `piva`) su create/update, `P2003` (FK: azienda con `Contact` collegati) su delete. Ogni Server Action ritorna sempre `{ success, error? }`, mai un throw per errori di validazione/vincolo attesi.
- `CompanyForm` è condiviso tra creazione e modifica: sceglie `createCompany` o `updateCompany.bind(null, companyId)` in base alla presenza di `defaultValues`, usa `useActionState` per pending state ed errori di validazione per campo. Se riceve un prop `onSuccess` lo richiama (usato da `NewCompanyButton` per chiudere il modale + `router.refresh()`); altrimenti fa `router.push("/companies")` lato client (usato dalla pagina di edit). L'azione non chiama mai `redirect()` di proposito, altrimenti il client non riceverebbe mai lo stato di successo.
- `zod` è stato aggiunto come dipendenza diretta in `package.json` (prima presente solo transitivamente via `prisma`).
- **Nota di disallineamento con questo file**: le pagine/azioni di Company sono state spostate dentro il route group `src/app/(dashboard)/companies/` (non più `src/app/companies/`, mai aggiornato qui sopra) e la creazione è passata da una route `/companies/new` dedicata a un modale (`NewCompanyButton` + `Modal` da `components/ui/`) aperto dalla pagina lista — l'edit resta invece una route separata (`[id]/edit/page.tsx`), non un modale. Anche `CompaniesTable`/la pagina lista ora aggregano dati di `Deal`/`Activity` per metriche e righe espandibili, non documentato qui. Il CRUD Contact sotto segue lo stato reale del codice, non questa sezione.

## CRUD Contact
- Stessa struttura di Company (Server Component lettura + Server Actions scrittura + Client Component solo dove serve interattività), dentro `src/app/(dashboard)/contacts/` (non `app/contacts/` in root — stesso motivo di Company: `app` sta in `src/app`). File: `app/(dashboard)/contacts/page.tsx`, `app/(dashboard)/contacts/[id]/edit/page.tsx`, `app/(dashboard)/contacts/actions.ts`, `components/contacts/{ContactForm,ContactsTable,NewContactButton,DeleteContactButton}.tsx`.
- **Verificato lo schema reale prima di scrivere lo Zod schema** (come richiesto, dopo la discrepanza già vista su `piva`/`address`): `Contact.name`/`Contact.surname` sono `String` obbligatori, `Contact.companyId` è `Int?` con relazione `company Company?` — quindi opzionale sia lato DB che nel form. Lo Zod schema in `actions.ts` usa `z.preprocess` per trasformare la stringa vuota del `<select>` ("Nessuna azienda") in `null` esplicito prima di validare `companyId` come `number.int().positive().nullable()` — necessario perché il campo deve poter essere esplicitamente "nessuna azienda" (FormData manda sempre una stringa, mai `undefined`, quindi `.optional()` da solo non bastava).
- `deleteContact` traduce `P2003` in "Impossibile eliminare: il contatto ha ancora trattative collegate." (stesso pattern di `deleteCompany`/`P2003`, ma qui il vincolo è `Deal.contactId`, obbligatorio e non nullable — a differenza di `Company.contacts`, cancellare un `Contact` con `Deal` collegate va sempre in conflitto, non c'è un caso "orfano" possibile).
- **Creazione via modale, non route `/contacts/new` dedicata**: la richiesta originale elencava una pagina `app/contacts/new/page.tsx` separata, ma lo stato reale attuale di Company (vedi nota sopra) usa già un modale (`NewCompanyButton`) per la creazione, senza più una route `/companies/new`. Per restare effettivamente "a specchio" del pattern Company oggi in uso (non di una sua versione precedente), Contact segue lo stesso modale: `NewContactButton` (in `components/contacts/`) apre `ContactForm` dentro `Modal` dalla pagina lista, passandogli l'elenco `companies` già caricato lì. `ContactForm` resta comunque riusabile anche in modalità "pagina piena" (route `[id]/edit/`, che non è un modale) perché il fallback `router.push("/contacts")` in assenza di `onSuccess` è invariato dal pattern Company.
- `ContactForm` usa `Input`/`Button` da `components/ui/` per i campi testo (a differenza di `CompanyForm`, che ad oggi usa ancora `<input>`/`<button>` grezzi non stilizzati — vedi nota disallineamento sopra su Company). Per il campo azienda non esiste un componente `Select` in `components/ui/`: è un `<select>` nativo con le stesse classi (bordo/bg/padding/focus) della variante `default` di `Input`, caso d'uso singolo non promosso a componente base (stesso criterio già usato altrove per dettagli one-off, es. bordo notifica in Topbar).
- **Nota di design richiesta esplicitamente**: `Contact` non ha un campo `createdByUserId` — scelta intenzionale, non omissione. A differenza di `Deal`/`Activity` (dove sapere "chi" è rilevante per responsabilità/riassegnazione — vedi nota `Activity.userId` sopra), i `Contact` sono dati collettivi del team: visibili e modificabili da qualunque utente autenticato, senza distinzione di proprietario.
- Verifica: `tsc --noEmit` ed `eslint` puliti su tutti i file nuovi. Non è stato possibile verificare a schermo nel browser (login richiede una password bcrypt valida; l'utente seed ha `passwordHash: "TEMP_PLAIN_TEXT"`, non un hash reale, e non è stato possibile impostarne una di test in questa sessione) — solo la redirect del proxy su `/contacts` senza sessione è stata verificata live.

## Design system (Northline CRM)
- Fonte: `design-system.md` in root (estratto da un mockup Figma/Claude Design). Per ora è stata portata solo l'infrastruttura di token in `src/app/globals.css` + `src/app/layout.tsx` — nessun componente visivo (Button, Card, ecc.) è stato ancora costruito.
- **Niente `tailwind.config.ts`, di proposito**: questo progetto usa Tailwind CSS **v4**, che ha abbandonato la config JS a favore della configurazione CSS-first via `@theme` (vedi `src/app/globals.css`). Un `tailwind.config.ts` richiederebbe la direttiva `@config` e andrebbe in conflitto/duplicazione con l'unico blocco `@theme inline` già presente. Se in futuro si è tentati di creare `tailwind.config.ts` per aggiungere token "alla v3", è quasi certamente l'abitudine sbagliata per questa versione — estendere invece `@theme` in `globals.css`.
- Tutti i colori/radius/shadow/spacing del design system sono token nominati dentro l'unico blocco `@theme inline` di `globals.css` (namespace Tailwind v4: `--color-*`, `--radius-*`, `--shadow-*`, `--spacing-*`, `--font-*`). I nomi ricalcano quelli del documento (`primary`, `surface-1/2/3`, `text-primary/secondary/muted`, `success`/`warning`/`danger` (+varianti `-bg`), `border`/`border-subtle`), con due aggiunte non esplicitamente elencate nella richiesta ma presenti nel documento: `primary-subtle` (`#26375C`, fondo tenue) e `primary-soft` (`#B9CCFF`, testo/link su sfondo scuro).
- `--color-background` è stato riusato (stesso nome dello scaffold di create-next-app) ma ripuntato al colore pagina del design system (`#0F171F`); è stato aggiunto un alias `--color-foreground: var(--color-text-primary)` solo per **retrocompatibilità** con `src/app/page.tsx` (pagina placeholder di create-next-app, non ancora toccata), che usa ancora le classi `bg-foreground`/`text-foreground`. Il blocco `@media (prefers-color-scheme: dark)` dello scaffold è stato rimosso: il design system non definisce una variante light (`design-system.md`, sezione "Non definito").
- Spacing e radius sono scale **nominali aggiuntive** (`--radius-checkbox/tooltip/icon/control/panel/card/modal/pill`), non sostituiscono la scala numerica di default di Tailwind (`p-4`, `gap-2`, `rounded-sm`, ecc. restano invariati e continuano a funzionare esattamente come prima).
- **Bug reale trovato e corretto costruendo `components/ui/`**: la prima scala `--spacing-*` (nomi t-shirt semplici: `--spacing-xs`, `--spacing-md`, `--spacing-lg`, ecc.) sembrava sicura per analogia con `--radius-*`, ma **non lo è**. Tailwind v4 usa lo stesso namespace `--container-*` (chiavi `xs`/`sm`/`md`/`lg`/`xl`/`2xl`/`3xl`/…) per `max-w-*`/`min-w-*`/`w-*`/`h-*`, e quando una chiave esiste sia in `--spacing-*` sia in `--container-*` **vince `--spacing-*`**. Il risultato: `--spacing-md: 14px` aveva silenziosamente rotto `max-w-md` in tutto il progetto (compresi `src/app/page.tsx`, non toccato, e `CompanyForm.tsx`) portandolo da 28rem a 14px. Non è successo con `--radius-*` solo perché quei nomi (`checkbox`, `card`, `modal`, ecc.) non sono nomi t-shirt e non potevano collidere. **Regola per qualunque token futuro**: prima di aggiungere una chiave a un namespace Tailwind esistente (`--spacing-*`, `--text-*`, `--radius-*`, `--shadow-*`, `--tracking-*`, …), verificare che quel nome non compaia già nello scaffold di default di Tailwind per QUALSIASI utility che condivide lo stesso namespace (non solo quella che si sta usando in quel momento) — in caso di dubbio, usare un nome non ambiguo invece di un t-shirt size. Fix applicato: tutta la scala `--spacing-*` custom ora usa il prefisso `nl-` (lo stesso delle `@keyframes nl-pulse`/`nl-flash` del mockup originale), quindi `gap-nl-md`, `py-nl-control-y`, ecc. — mai `gap-md`/`py-control-y` nudi.
- Font: `Fraunces` (`--font-display`), `Inter` (`--font-sans`), `IBM Plex Mono` (`--font-mono`) caricati via `next/font/google` in `src/app/layout.tsx` con solo i pesi effettivamente usati nel documento (400/500/600, 400/500/600/700, 400/500). Sostituiscono Geist/Geist Mono dello scaffold iniziale, non più referenziati da nessuna parte.
- `--gradient-logo` (gradiente logo) è una CSS custom property in `:root`, fuori dal blocco `@theme`: `--gradient-*` non è un namespace riconosciuto da Tailwind v4 e non genererebbe alcuna utility; va usato con una classe arbitraria (`bg-[image:var(--gradient-logo)]`) quando si costruirà il componente Logo.
- Non ancora portate (rimandate a quando si costruiranno i componenti che le usano): le animazioni `nl-pulse`/`nl-flash` (pallino "trattativa calda", flash riga nuova trattativa) — sono comportamento di componente, non token di base.
- `lucide-react` aggiunto come dipendenza per le icone: il documento specifica size 15–19px e `strokeWidth` 1.8, da passare come props a ogni icona (vedi uso in `src/app/ui-preview/page.tsx`).

## Componenti UI di base (`src/components/ui/`)
- Primi componenti costruiti sul design system: `Button`, `Input`, `Badge`, `Dot` (più `index.ts` che li ri-esporta). Nessuno ha `"use client"`: sono wrapper presentazionali senza hook/stato proprio, pensati per restare renderizzabili anche da Server Component — l'interattività (event handler) la porta chi li usa, come già fa `CompanyForm`.
- **Due scelte di design non specificate nel documento** (segnalate esplicitamente, come richiesto):

## Storage file (R2)
- Provider: Cloudflare R2 (S3-compatible), scelto per l'egress gratuito verso l'app Next.js (a differenza di S3 "vero", dove il traffico in uscita ha costo) — via `@aws-sdk/client-s3`/`@aws-sdk/s3-request-presigner` (protocollo S3, non un SDK Cloudflare dedicato).
- Pattern adottato: **presigned URL**, upload diretto browser -> bucket. Il server Next.js genera solo l'URL firmato (`createPresignedUploadUrl`), non riceve mai i byte del file: evita i limiti di payload/timeout delle funzioni serverless (Vercel) che un upload proxy-ato dal server incontrerebbe con file più grandi.
- Codice infrastruttura: `src/lib/storage.ts` (`createPresignedUploadUrl`, client S3 per R2). Server Action: `src/app/(dashboard)/attachments/actions.ts` — `requestUploadUrl`/`confirmUpload`/`deleteAttachment`, non ancora collegate a nessuna UI (Server Action pronte per essere importate, arriverà in uno step successivo).
- **Correzione di scope**: una prima versione delle Server Action accettava sia `dealId` sia `contactId` (uno dei due, mai entrambi/nessuno), rispecchiando la nullabilità di entrambi i campi in `Attachment`. È stata poi semplificata: **un Attachment si collega solo a una `Deal`**, `contactId` non è più un parametro di `requestUploadUrl`/`confirmUpload` e viene sempre scritto come `null` in `confirmUpload`. Il campo resta nello schema Prisma (nullable, per non fare una migrazione solo per questo), ma è morto lato applicativo finché non nascerà un caso d'uso reale per allegati su `Contact`.
- `requestUploadUrl(fileName, mimeType, fileSize, dealId)`: `requireAuth()` → verifica che la `Deal` esista e sia visibile all'utente corrente con lo stesso filtro per ruolo delle altre Server Action su Deal (`ownRowsWhere`, vedi `updateDealState` in `deals/actions.ts`: un non-admin vede solo le proprie) → chiama `createPresignedUploadUrl`, propagando un eventuale `Error` come `{ success: false, error }`.
- `confirmUpload(storageKey, fileName, mimeType, fileSize, dealId)`: `requireAuth()` → **ri-verifica** la visibilità della Deal (stesso controllo di `requestUploadUrl`, ripetuto perché sono due Server Action indipendenti e la seconda può essere chiamata senza essere passati dalla prima) → `HeadObjectCommand` su R2: se l'oggetto non esiste o `ContentLength`/`ContentType` non coincidono esattamente con quanto dichiarato (nessuna tolleranza), errore e nessuna scrittura → solo se tutto torna, `prisma.attachment.create` con `uploadedByUserId` dall'utente corrente e `contactId: null`; `P2002`/`P2003` tradotti in messaggi utente come nel resto del progetto.
- `deleteAttachment(attachmentId)`: `requireAuth()` → recupera l'`Attachment` (404 applicativo se non esiste) → stessa verifica di ownership Deal di `requestUploadUrl`/`confirmUpload` (`ownRowsWhere` sulla `Deal` collegata, non un controllo diverso o più permissivo) → **prima** `DeleteObjectCommand` su R2 con `Key: storageKey`, **poi** solo se quello ha successo `prisma.attachment.delete`. Ordine intenzionale: se R2 fallisce si ritorna errore senza toccare il DB (la riga resta come riferimento del file ancora presente, l'utente può ritentare); l'ordine opposto rischierebbe un file orfano su R2 senza più alcuna riga da cui ripulirlo. Usa `s3Client`/`DeleteObjectCommand` direttamente nella Server Action (stesso criterio già usato per `HeadObjectCommand` in `confirmUpload`), non una funzione wrapper in `storage.ts` — coerenza con quel precedente più che con `createPresignedUploadUrl` (che invece è un wrapper, ma incapsula anche validazione/firma URL, non una singola chiamata SDK diretta).
  - **Nota su R2/S3 e oggetti già assenti**: `DeleteObjectCommand` su S3 (e R2, compatibile) è idempotente — non lancia errore se la `Key` non esiste già (risponde comunque "successo"). Il ramo di errore R2 in `deleteAttachment` intercetta quindi solo problemi reali (rete, credenziali, bucket errato), non il caso "il file era già stato rimosso manualmente dal bucket": in quel caso la delete R2 "riesce" comunque (no-op) e si procede a cancellare la riga DB — comportamento voluto, l'obiettivo finale (nessun file, nessuna riga) resta raggiunto.
  - **Nota su `dealId` nullable ma sempre valorizzato**: `Attachment.dealId` resta `Int?` a schema, ma le Server Action esistenti lo valorizzano sempre. Se `deleteAttachment` trovasse comunque un `Attachment` con `dealId: null` (stato che il codice attuale non produce), nega per sicurezza con lo stesso messaggio "non trovato" invece di decidere una visibilità di default — nessun `ownRowsWhere` è applicabile senza una Deal a cui ancorarlo.
  - **Race condition sulla riga DB**: se la riga `Attachment` viene già cancellata da un'altra richiesta tra la lettura iniziale e la `delete()` (es. doppio click), il `P2025` risultante è trattato come successo, non errore — stesso pattern già usato in `logout()` (`src/lib/session.ts`) per `Session`.
- `createPresignedUploadUrl(fileName, mimeType, fileSize)`: valida `mimeType` (whitelist `application/pdf`/`image/png`/`image/jpeg`) e `fileSize` (max 10MB) lanciando un errore descrittivo se non passano; genera uno `storageKey` come UUID (mantenendo l'estensione originale del `fileName`, mai il nome file com'è); firma un `PutObjectCommand` con `ContentType`/`ContentLength` inclusi nella firma (upload di tipo/dimensione diversi da quelli dichiarati vengono rifiutati da R2 stesso, non solo dal controllo lato server); scadenza URL 300 secondi.
- Variabili d'ambiente richieste (già in `.env`, non generate qui): `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`.
- **Nota di disallineamento nome variabile**: nonostante il nome, `R2_ACCOUNT_ID` in questo progetto contiene già l'endpoint R2 completo (`https://<account-id>.r2.cloudflarestorage.com`), non il solo account id esadecimale — verificato leggendo il valore reale in `.env` prima di scrivere il codice (stesso principio già seguito per lo schema Prisma reale in altre sezioni di questo file). `storage.ts` lo usa quindi direttamente come `endpoint` di `S3Client`, senza concatenarlo in un URL. Se in futuro la variabile viene corretta per contenere solo l'account id, il codice va aggiornato di conseguenza.
- **Nessun file `.env.example`/simile esisteva nel progetto**: non ne è stato creato uno nuovo (fuori scope di questo step, non richiesto esplicitamente in assenza di un file preesistente da aggiornare).
- Decisioni non specificate esplicitamente, segnalate come richiesto:
  - **Estensione file mancante**: se `fileName` non ha un'estensione (nessun `.`), `storageKey` è il solo UUID senza estensione — nessun fallback/estensione di default inventata.
  - **`R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET_NAME` non definite**: nessun controllo esplicito a runtime né errore custom — stesso pattern già in uso per `SESSION_SECRET` in `src/lib/session.ts` (cast diretto `as string`, nessun fallback). Se mancanti, l'errore arriva dall'SDK AWS/da R2 stesso (credenziali non valide, endpoint `undefined`), non da un messaggio applicativo dedicato.
  - **Validazione lato server vs firma URL**: la validazione di `mimeType`/`fileSize` in `createPresignedUploadUrl` è un fail-fast prima di generare l'URL (evita di chiamare R2 per una richiesta già invalida), ma il vincolo che conta davvero è quello firmato nell'URL (`ContentType`/`ContentLength`) — un client che chiamasse l'endpoint R2 direttamente con un file diverso verrebbe comunque rifiutato da R2, non solo dal controllo qui.
- `createPresignedDownloadUrl(storageKey)`: stesso client/pattern, `GetObjectCommand` invece di `PutObjectCommand`, stessa scadenza 300s (nessun motivo per differenziarla da quella di upload). Server Action: `getDownloadUrl(attachmentId)` in `attachments/actions.ts` — stessa ownership di `deleteAttachment` (vedi sotto), poi genera l'URL.
- **Bucket R2: serve una policy CORS per l'upload diretto da browser**, non scontata di default — il pattern presigned URL richiede che il browser faccia una PUT cross-origin verso `*.r2.cloudflarestorage.com`, bloccata dal browser stesso (preflight CORS) finché il bucket non dichiara esplicitamente l'origin dell'app tra quelli ammessi. Scoperto verificando il flusso end-to-end in browser (upload reale bloccato da `Access-Control-Allow-Origin` mancante) prima di considerare il frontend completo; configurazione applicata direttamente sul bucket (fuori da questo repo, nessun file di configurazione da versionare).
- `deleteAttachment(attachmentId)` esposto anche a `getDownloadUrl` tramite un helper comune (`loadAccessibleAttachment` in `attachments/actions.ts`): recupera l'Attachment e verifica la Deal collegata in un solo punto, invece di ripetere la stessa sequenza findUnique+ownership in entrambe le Server Action.
